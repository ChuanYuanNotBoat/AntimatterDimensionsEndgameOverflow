# ADE 最小成本整体加固计划

日期：2026-09-20（Asia/Singapore）  
状态：已选定执行方向

## 1. 决策

采用“**本地 ADE 主线整体加固，选择性吸收 ADbe**”路线。

- 本地 ADE HEAD `ab358cf39a766e8c4c0e8b8fc44a95f185d82a41` 是功能、数值行为和存档兼容的真源。
- ADbe refactor `14fcf1156011a36240e23c712dcf1e54fa01782f` 是数值设计、核心实现和工程结构的供体。
- 不进行整仓换底，不要求 Git 历史从 ADbe 分叉。
- 不先移植 ADE 原版再重放用户修改。
- 目标是让本地 ADE 在高风险核心上逐步与 ADbe 的正确设计趋同，同时保留全部 ADE Endgame 内容。

这不是继续零散修补。加固必须围绕统一数值契约、存档契约和自动回归测试展开。

## 2. 为什么选择这条路线

已验证的成本和风险依据：

- 本地 ADE 相对共同上游有 10 个提交、97 个源码文件变化，包含数值修复、倍率分析和测试体系。
- ADbe 缺少本地 ADE 的约 229 个源码文件；若以 ADbe 为底座，需要重新迁入大量 Endgame 系统。
- 本地补丁在 ADbe refactor 上仅 31/97 个源码文件能通过纯补丁上下文检查。
- 两边已经使用 `break_eternity`；换底本身不会消除 `.toNumber()`、`Math.*`、零值对数和中间 Infinity 等问题。
- 当前本地基线已有 280 项测试通过，可直接作为加固安全网。

因此，最低成本方案是修复真正的数值边界和存档边界，而不是支付完整架构迁移成本。

## 3. 目标与非目标

### 目标

1. 消除主要进度路径上的 NaN、非预期 Infinity、Number 溢出和 Decimal 类型破坏。
2. 统一经济数值的类型与边界规则，停止按故障点临时打补丁。
3. 保证现有 ADE 存档可继续加载、导出和推进。
4. 保留当前全部 ADE Endgame 功能和用户自定义行为。
5. 能够低成本选择性引入 ADbe 后续的数值修复。
6. 建立 golden-save 回归，使后续修改可验证。
7. 在不改变数值语义的前提下，优化已经测量出的运行热点，重点改善后期存档、离线模拟和高频 UI 更新。

### 本阶段非目标

- 不整体迁移到 ADbe refactor。
- 不重建 ADbe 缺少的全部 ADE 内容模块。
- 不同时切换 Vite、Vue 2.7、i18n 和全部目录结构。
- 不重写游戏平衡。
- 不做没有基准数据支撑的全局微优化，也不为性能目的把无界 Decimal 降为 Number。
- 不移植 `ade-web` 静态 bundle；部署产物始终从稳定源码重新构建。
- 不为满足“基于 ADbe”的名义要求改写 Git 历史。

## 4. 核心设计规则

### 4.1 数值契约

- 经济量、倍率、价格、资源和奖励默认保持为 `Decimal`。
- `Number` 只用于明确有界的数量：数组索引、布尔计数、UI 尺寸和经过证明的短时间值。
- 禁止在 gameplay 核心中任意调用 `.toNumber()`；每个转换必须说明允许范围和溢出处理。
- 禁止把 `Decimal` 直接传入 `Math.log*`、`Math.pow`、`Math.exp`、`Math.min/max`。
- 对乘积、幂、求和、比值和对数建立集中式安全 helper。
- `log10(0)`、负数对数、`Infinity/Infinity`、`0 * Infinity` 必须有明确领域语义。
- 饱和值、拒绝值和“保持 Infinity”是三种不同策略，必须由业务规则选择，不能统一盲目 clamp。
- format/notation 只负责展示，不能反向参与 gameplay 计算。

### 4.2 存档契约

- 现有 ADE 前缀和 schema 继续受支持。
- 存档来源格式、ADE schema 版本和未来引擎迁移版本分开记录，不能共用一个递增数字。
- 迁移器必须保留未知字段的审计记录。
- 首次执行高风险转换时只生成新存档，不覆盖用户原始存档。
- 任何存档兼容改动必须通过旧档加载、一个 tick、关键操作、导出和重新导入测试。

### 4.3 ADbe 吸收规则

每项 ADbe 改动都按以下顺序处理：

1. 先确认它解决的实际问题和依赖。
2. 提取最小算法或接口，不直接复制整个模块树。
3. 适配本地 player schema 和 ADE Endgame 规则。
4. 补上针对本地 golden save 的回归测试。
5. 单独提交，便于撤销和追踪来源。

### 4.4 性能优化规则

- 先测量再优化；没有可重复基准或 profiler 证据的代码不进入性能工作流。
- 基准固定存档、随机种子、模拟时长、浏览器版本和测试步骤，记录中位数、P95 和峰值内存。
- 性能优化不能改变资源结果、购买数量、事件顺序或存档结构；如允许误差，必须为该字段单独定义容差。
- 禁止用 `.toNumber()`、降低精度或提前 clamp 掩盖计算成本。
- 优先处理高收益、低耦合热点：同一 tick 内的重复倍率求值、循环内不变量、批量购买逐项循环、离线模拟步进、重复格式化和隐藏标签页的响应式更新。
- 缓存必须有明确失效条件；不能依赖“下一 tick 总会刷新”的隐式行为。
- 性能提交与行为修复分开，并附带优化前后数据。
- 以相对基准而非固定 FPS 为验收依据；不同机器只比较同一环境中的前后结果。

## 5. 分阶段执行计划

### 阶段 0：冻结基线与最小 PoC（3–5 人日）

任务：

- 固定 ADE、ADE 上游和 ADbe 的三个 SHA。
- 将现有 280 项测试纳入统一入口。
- 建立无进度、中期、Reality 前后、Ra、Laitela、Machine、Singularity 和极端溢出存档矩阵。
- 给 golden save 记录关键字段断言，不在仓库中提交真实私人存档。
- 建立性能基线：正常/后期 `gameLoop`、1 小时/24 小时离线模拟、存档加载、批量购买和倍率分析页面更新。
- 选择 Currency/gameLoop 作为 ADbe 算法吸收 PoC。
- 明确 `false &&` 禁用被动 TP 是正式规则、临时保护还是待修 Bug。

退出条件：

- 所有现有测试仍然通过。
- 至少一个真实极端存档可重复运行检查流程。
- 基准可以在相同环境中重复运行，结果波动范围已记录。
- PoC 证明可以只吸收 ADbe 的局部能力而不牵动全部 UI 和内容系统。

### 阶段 1：统一数值基础设施（4–7 人日）

任务：

- 审核并收敛 `finite-decimal.js`、bulk purchase 和现有 bounded helpers。
- 增加 Decimal/Number 边界 API，并为每种转换建立明确命名。
- 为危险运算建立集中 helper：safe ratio、positive log、bounded power/product/sum。
- 增加静态检查清单，阻止新增无说明的 `.toNumber()` 和 Decimal→`Math.*`。
- 统一 NaN、Infinity、负值和表示上限的处理策略。

退出条件：

- helper 具备边界单元测试。
- 新代码不再直接引入未经审查的危险转换。
- 不改变正常范围内的平衡结果。

### 阶段 2：高风险 gameplay 域加固（7–12 人日）

按以下顺序执行，每个域单独提交并独立回归：

1. Currency setter、`gameLoop`、离线模拟。
2. IP、EP、TP 与 Reality rewards。
3. AD、ID、TD、CD、DD 和 Tickspeed。
4. Ra alchemy、Laitela、Dark Matter。
5. Machines、Singularity、hybrid rebuyables、autobuyers。
6. Glyph、Replicanti 和剩余指数增长路径。

退出条件：

- 对应 golden save 能加载并运行完整 tick。
- 关键购买、prestige 和 Reality 操作不产生非预期 NaN/Infinity。
- 正常区间结果与冻结基线一致；必要变化有独立说明。

### 阶段 3：存档与格式边界加固（4–7 人日）

任务：

- 为存档来源格式和 schema 版本建立独立字段或可靠推断层。
- 建立只读检查、显式转换、另存和回滚流程。
- 检查 player deep merge、缺省字段和 Decimal 反序列化。
- 审查 `format`、notations 与 gameplay 数值之间的泄漏。
- 加入 corrupted、缺字段、旧版本、超大 Decimal 和多玩家容器测试。

退出条件：

- golden save 完成加载 → tick → 操作 → 导出 → 重载闭环。
- 原始存档始终可保留。
- 格式化失败不会改变游戏状态。

### 阶段 4：测量驱动的性能优化（3–6 人日）

只优化阶段 0 基准或 profiler 已确认的热点。候选任务按收益优先级选择，不要求全部执行：

1. 将同一 tick 内重复计算且输入不变的倍率提升为局部复用。
2. 为高成本派生值增加带显式失效条件的缓存。
3. 将可证明等价的逐次购买循环替换为 bulk 公式。
4. 把 `gameLoop` 和离线模拟中的循环不变量移出内层循环。
5. 合并同一帧内重复的事件、响应式更新和统计刷新。
6. 暂停隐藏标签页或不可见组件的高频 format 与 multiplier tree 重算。
7. 仅在逐字段结果等价时，调整离线模拟的分块大小或安全步进策略。
8. 减少存档导入过程中的重复解析、deep clone 和 Decimal 重建。

退出条件：

- 每项优化都有相同环境下的前后基准和对应回归测试。
- 被选中的主要热点目标改善至少 20%，或有明确证据表明继续优化不具成本效益。
- 正常流程的 P95 不得恶化超过 10%，峰值内存不得无说明地增加超过 10%。
- golden-save 的关键数值、购买结果和事件顺序保持一致。

### 阶段 5：全量回归与交付（4–7 人日）

任务：

- 运行单元、源码、golden-save 和浏览器 smoke 测试。
- 重跑性能基线，确认后期 `gameLoop`、离线模拟、加载和 UI 热点没有回退。
- 审查倍率分析公式与 gameplay 实际公式是否一致。
- 构建新的部署产物并写入可追溯 SHA。
- 编写变更说明、存档备份提示和已知限制。

退出条件：

- 自动测试全绿。
- 关键 golden-save 流程全绿。
- 无阻断级数值或存档问题。
- 原 ADE 工作线仍可回退使用。

## 7. 工作方式

- 所有实验在独立 worktree 或隔离目录进行。
- 原项目主工作树保持可运行，不在其中做破坏性切换。
- 每个提交只处理一个数值域或一个兼容契约。
- 先写失败测试或保存重现场景，再修改实现。
- 性能提交先保存基准结果，并与功能修复分开。
- 每完成一个阶段，都允许停止并交付，不要求为了“整体迁移”继续扩大范围。
- ADbe 新提交只在解决当前明确问题时引入，不持续追逐其 refactor HEAD。

## 8. 重新评估完整迁移的触发条件

只有出现以下任一情况，才重新讨论以 ADbe 为实际底座：

- 本地核心与 ADbe 的同类修复长期重复，选择性吸收成本持续超过直接迁移成本。
- 必须长期跟随 ADbe 上游发布或与其生态保持 API 兼容。
- 产品决定删除或重做大量 ADE Endgame 内容，使 229 个本地独有源码文件不再需要保留。
- 当前加固累计工作明显超过 44 人日，且主要成本来自旧底座结构而非 ADE 内容本身。

在这些条件出现前，不为架构纯粹性支付 85–145 人日的整仓换底成本。

## 11. 按复杂度分配模型

### 11.1 模型角色

正式模型 ID 使用 `gpt-5.6-sol`、`gpt-5.6-terra` 和 `gpt-5.6-luna`。本文中的 Luna 即用户所称 Lunar。

| 层级 | 模型 | 推荐推理强度 | 适用范围 |
|---|---|---|---|
| 高复杂度/高风险 | `gpt-5.6-sol` | `high`；架构关卡用 `xhigh` | 数值语义、存档架构、跨模块设计、难复现溢出、离线算法、最终审查与放行 |
| 中复杂度/默认实现 | `gpt-5.6-terra` | `medium`；复杂实现用 `high` | 大多数编码、局部重构、浏览器调试、性能分析、集成测试与缺陷修复 |
| 低复杂度/高重复度 | `gpt-5.6-luna` | `low` 或 `medium` | 只读扫描、调用点清单、测试批量执行、基准采集、格式整理和明确模板下的小改动 |

模型选择依据遵循 OpenAI 官方说明：[Sol 用于复杂专业工作，Terra 平衡智能与成本，Luna 面向成本敏感的高吞吐任务](https://developers.openai.com/api/docs/models)；在 Codex 子智能体工作流中，[Luna 适合范围明确且重复的任务，Terra 适合快速扫描和辅助工作，而复杂多步骤任务优先使用 Sol](https://developers.openai.com/zh-Hans/docs/agent-configuration/subagents)。

### 11.3 升级与降级规则

- Luna 遇到需求含糊、测试预期不明确、需要修改 gameplay 或出现多种合理实现时，立即升级 Terra。
- Terra 遇到跨 prestige 层、存档不可逆转换、数值语义不确定、离线结果不守恒或三个以上模块联动时，升级 Sol。
- Sol 先产出契约、决策和验收标准；已有清晰规格后的实现尽量交回 Terra，机械验证交给 Luna。
- Luna 的代码改动必须范围明确且可自动验证；不得单独合入数值核心、存档迁移或离线模拟改动。
- Terra 编写的高风险实现必须由 Sol 复核；普通 UI、测试和局部重构不强制 Sol 复核。
- 任务不能仅按文件数量判断复杂度；一个一行的 schema 版本判断可能比几十个测试文件更高风险。
- 同一文件同时包含机械修改和高风险逻辑时拆成两个任务，分别分配模型。

### 11.4 建议工作量占比

为兼顾质量与成本，按实际智能体工作时间估算：

| 模型 | 建议占比 | 主要用途 |
|---|---:|---|
| Sol | 15–25% | 架构、数值/存档语义、疑难问题、关卡评审 |
| Terra | 50–65% | 主要实现、调试、集成和性能优化 |
| Luna | 15–25% | 扫描、测试、基准、清单和文档 |

占比是预算护栏，不是硬指标。若 Sol 发现契约尚未稳定，应先暂停 Terra/Luna 的批量实现；若任务已经完全规格化，则应主动降级给 Terra 或 Luna，避免为机械工作支付最高模型成本。
